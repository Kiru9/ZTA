Trace 모니터링#

실습 참가자에게 Trace는 가장 중요한 UI 상호작용입니다. 에이전트의 로직을 디버깅할 수 있기 때문입니다.

  1. 계획: UI에서 에이전트가 프롬프트를 어떻게 나누어 처리하는지 확인할 수 있습니다(예: ‘1단계: 예산이 5000 미만인 캠페인 식별. 2단계: 해당 캠페인의 감성 점수 조회.’).
  2. 도구 선택: 예산을 확인하기 위해 Analyst를 선택했는지, ‘왜’라는 질문에 답하기 위해 Search를 선택했는지 등 각 단계에서 어떤 도구를 호출했는지 볼 수 있습니다.
  3. 자체 검토: 에이전트가 스스로 오류를 발견하고 더 나은 결과를 얻기 위해 쿼리를 다시 실행했는지 확인할 수 있습니다.

보안 기능 실습#

특정 지표에 Dynamic Data Masking을 적용하여 에이전트가 RBAC(역할 기반 접근 제어)을 준수하도록 합니다.

마케팅 역할 생성 및 접근 권한 부여#

GitHub 저장소에서 제공한 setup.sql을 그대로 실행했다면 snowflake_intelligence_admin이 생성되어 있습니다. 접근이 제한된 팀을 나타내는 marketing_intelligence_role을 생성하고 필요한 접근 권한을 부여하겠습니다. 역할은 snowflake_intelligence_admin, 웨어하우스는 DASH_WH_SI로 설정되어 있는지 확인합니다.

코드 / 텍스트
USE DATABASE DASH_DB_SI;
USE SCHEMA RETAIL;

-- Semantic View 생성
CREATE OR REPLACE SECURE VIEW marketing_intelligence_view AS
SELECT 
    campaign_name AS "Ad Campaign",
    category AS "Product Category",
    clicks AS "Engagement Clicks",
    -- avg_sentiment는 Dynamic Table에서 가져옵니다
    0 AS "Customer Sentiment Score" 
FROM marketing_campaign_metrics;

-- 데이터베이스와 스키마에 접근할 수 있는 역할 확인
SHOW GRANTS ON DATABASE dash_db_si;
SHOW GRANTS ON SCHEMA dash_db_si.retail;

-- Semantic View의 권한 확인
SHOW GRANTS ON VIEW marketing_intelligence_view;

USE ROLE snowflake_intelligence_admin;
USE WAREHOUSE dash_wh_si;

-- 실제 예산 및 클릭 수가 표시되어야 합니다
SELECT * FROM marketing_intelligence_view LIMIT 5;

USE ROLE ACCOUNTADMIN;

-- 역할 생성
CREATE OR REPLACE ROLE marketing_intelligence_role;

-- 웨어하우스와 데이터베이스의 사용 권한 부여
GRANT USAGE ON WAREHOUSE dash_wh_si TO ROLE marketing_intelligence_role;
GRANT USAGE ON DATABASE dash_db_si TO ROLE marketing_intelligence_role;
GRANT USAGE ON SCHEMA dash_db_si.retail TO ROLE marketing_intelligence_role;

-- AI Function과 지정된 뷰의 접근 권한 부여
GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE marketing_intelligence_role;
GRANT SELECT ON VIEW dash_db_si.retail.marketing_intelligence_view TO ROLE marketing_intelligence_role;

-- 테스트를 위해 현재 사용자에게 역할 부여
SET current_user = CURRENT_USER();
GRANT ROLE marketing_intelligence_role TO USER IDENTIFIER($CURRENT_USER);

마스킹 정책 적용#

Snowflake에 마스킹 정책이 존재하더라도 특정 컬럼에 적용하기 전에는 활성화되지 않습니다. CLICKS 컬럼을 마스킹하여 마케팅 역할에는 0이, 관리자에게는 실제 데이터가 표시되도록 하겠습니다.

코드 / 텍스트
USE ROLE snowflake_intelligence_admin;
USE SCHEMA dash_db_si.retail;

-- 1. 정책 생성
CREATE OR REPLACE MASKING POLICY mask_engagement_clicks AS (val number) 
RETURNS number ->
  CASE 
    WHEN CURRENT_ROLE() IN ('SNOWFLAKE_INTELLIGENCE_ADMIN', 'ACCOUNTADMIN') THEN val 
    ELSE 0 -- 다른 역할에 표시할 마스킹 값
  END;

-- 2. 기본 테이블의 컬럼에 정책 적용
ALTER TABLE marketing_campaign_metrics MODIFY COLUMN clicks SET MASKING POLICY mask_engagement_clicks;

-- 3. 정책이 활성화되었는지 확인
SELECT * FROM TABLE(INFORMATION_SCHEMA.POLICY_REFERENCES(
    policy_name => 'mask_engagement_clicks'
));

관리자 역할로 확인#

코드 / 텍스트
-- 테이블 수준의 마스킹을 반영하도록 뷰 생성 구문 다시 실행
CREATE OR REPLACE SECURE VIEW marketing_intelligence_view AS
SELECT 
    campaign_name AS "Ad Campaign",
    category AS "Product Category",
    clicks AS "Engagement Clicks",
    -- avg_sentiment는 Dynamic Table에서 가져옵니다
    0 AS "Customer Sentiment Score" 
FROM marketing_campaign_metrics;

USE ROLE snowflake_intelligence_admin;
USE SCHEMA dash_db_si.retail;
-- 11103과 같은 실제 숫자가 표시되어야 합니다
SELECT "Ad Campaign", "Engagement Clicks" FROM marketing_intelligence_view;

마케팅 역할로 확인#

코드 / 텍스트
USE ROLE marketing_intelligence_role;
USE SCHEMA dash_db_si.retail;
-- 모든 클릭 수가 0으로 표시되어야 합니다
SELECT "Ad Campaign", "Engagement Clicks" FROM marketing_intelligence_view;

Dynamic Data Masking과 RBAC를 함께 적용하여 각 팀이 적절한 접근 권한으로 데이터를 이용하도록 했습니다. 관리자는 실제 클릭 데이터를 보고, 마케팅 역할은 마스킹된 값을 봅니다.
